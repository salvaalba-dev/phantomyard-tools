# Work prompt — recorder lane, part 2 (v0): the bridge reports the recorder; the person asks before convening

This is a hand-off prompt for an external agent working on this repository. It describes work that is
**agreed** with the maintainer: implement it as specified, do not redesign it.

## Context

Part 1 (the recorder guardian) is already done: `phantommeet/tools/recorder-guardian.sh` + systemd
timer/oneshot, which raises the recorder when it is unhealthy, with no state of its own and without
ever touching a live recording. See the corresponding PR.

Part 2 closes the other half of the same problem: today a person convening a meeting cannot know
whether the recorder is ready until someone presses Record. Two pieces:

## 1. Project piece — `phantombridge` reports recorder readiness (read-only)

- Add a **read-only** recorder capability to the bridge, surfaced in the existing `/status` output
  (same shape/pattern as the existing recordings capability): whether the recorder is ready, and if
  not, which item is failing.
- How: query the host recorder's **local** health API (`http://127.0.0.1:2222/jibri/api/v1.0/health`,
  `status.busyStatus` / `status.health.healthStatus`) or, as a fallback, the state of the recorder's
  systemd units. Choose one primary source, document it, and degrade gracefully when the answer is
  unknown.
- Contract: the bridge only **reports**; it never starts or restarts anything, and it must never
  expose the recorder's unauthenticated API to the network.
- The readiness must be reachable through the path a persona already uses (the existing authenticated
  `/status`). Do **not** add a new public endpoint.

## 2. Procedural piece — the person asks before convening

- Where: the meeting workflow step where the responsible person convenes (the invitation tool). This
  is a procedural line, not a new verb and not a new endpoint.
- Behaviour: before sending the invitation, ask for recorder readiness through the bridge.
  - ready -> send the invitation exactly as today;
  - not ready -> **do not** send it, and notify the responsible person with the failing item;
  - `--force` -> convene without recording, with a warning.
- Note the existing transport: the bridge's `/status` is authenticated (admin token). Reuse that
  authenticated path; do not weaken it.

## 3. Docs, tests, changelog

- Update the SPEC (the capabilities table and the meeting-workflow section) and the component docs;
  add tests for the bridge's readiness reporting and for the procedural gate; add a CHANGELOG entry.
- Document the honest limits: the Jitsi **Record button cannot be hooked**; meetings convened by
  reusing a link, or running past their declared end, are not covered by this gate — the permanent
  guardian is what covers them; and readiness is a snapshot at convening time, not a promise for
  meeting time.
